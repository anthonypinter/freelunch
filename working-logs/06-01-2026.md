### 3. Full SQL Written for Backend Setup

Complete SQL covering:
- `profiles` table (with `is_admin`, `display_name`, `username`, `avatar_url`)
- `semesters` table
- `meals` table (with `status` CHECK constraint: `pending` / `approved` / `rejected`)
- RLS enabled on all three tables
- Policies: public read of approved meals, users see own meals, admins see all, admins can update status
- Trigger: `handle_new_user()` auto-creates empty profile row on signup (SECURITY DEFINER)
- Leaderboard views joining with `profiles` to return `display_name` and `username`
- Summer 2026 semester seeded

```sql
-- profiles
CREATE TABLE profiles (
  id            uuid PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  display_name  text,
  username      text UNIQUE,
  avatar_url    text,
  is_admin      boolean NOT NULL DEFAULT false,
  created_at    timestamptz DEFAULT now()
);

-- semesters
CREATE TABLE semesters (
  id          uuid DEFAULT gen_random_uuid() PRIMARY KEY,
  name        text NOT NULL,
  start_date  date NOT NULL,
  end_date    date NOT NULL
);

-- meals
CREATE TABLE meals (
  id          uuid DEFAULT gen_random_uuid() PRIMARY KEY,
  user_id     uuid REFERENCES auth.users(id) ON DELETE CASCADE,
  description text NOT NULL,
  how_to_get  text NOT NULL,
  photo_url   text,
  semester_id uuid REFERENCES semesters(id),
  status      text NOT NULL DEFAULT 'pending'
                CHECK (status IN ('pending', 'approved', 'rejected')),
  created_at  timestamptz DEFAULT now()
);

-- RLS
ALTER TABLE profiles  ENABLE ROW LEVEL SECURITY;
ALTER TABLE semesters ENABLE ROW LEVEL SECURITY;
ALTER TABLE meals     ENABLE ROW LEVEL SECURITY;

-- Profile policies
CREATE POLICY "Profiles are publicly readable"    ON profiles FOR SELECT USING (true);
CREATE POLICY "Users can insert their own profile" ON profiles FOR INSERT WITH CHECK (auth.uid() = id);
CREATE POLICY "Users can update their own profile" ON profiles FOR UPDATE USING (auth.uid() = id);

-- Semester policies
CREATE POLICY "Semesters are publicly readable" ON semesters FOR SELECT USING (true);

-- Meal policies
CREATE POLICY "Approved meals are publicly viewable" ON meals FOR SELECT USING (status = 'approved');
CREATE POLICY "Users can view their own meals"       ON meals FOR SELECT USING (auth.uid() = user_id);
CREATE POLICY "Admins can view all meals"            ON meals FOR SELECT USING (
  EXISTS (SELECT 1 FROM profiles WHERE id = auth.uid() AND is_admin = true)
);
CREATE POLICY "Users can insert their own meals" ON meals FOR INSERT WITH CHECK (auth.uid() = user_id);
CREATE POLICY "Users can delete their own meals" ON meals FOR DELETE USING (auth.uid() = user_id);
CREATE POLICY "Admins can update meal status"    ON meals FOR UPDATE USING (
  EXISTS (SELECT 1 FROM profiles WHERE id = auth.uid() AND is_admin = true)
);

-- Auto-create profile on signup
CREATE OR REPLACE FUNCTION public.handle_new_user()
RETURNS TRIGGER AS $$
BEGIN
  INSERT INTO public.profiles (id) VALUES (NEW.id) ON CONFLICT (id) DO NOTHING;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE TRIGGER on_auth_user_created
  AFTER INSERT ON auth.users
  FOR EACH ROW EXECUTE PROCEDURE public.handle_new_user();

-- Leaderboard views (join profiles for display names, approved meals only)
CREATE VIEW leaderboard_weekly AS
SELECT m.user_id, p.display_name, p.username, COUNT(*) AS meal_count
FROM meals m JOIN profiles p ON p.id = m.user_id
WHERE m.status = 'approved' AND m.created_at >= now() - interval '7 days'
GROUP BY m.user_id, p.display_name, p.username ORDER BY meal_count DESC;

CREATE VIEW leaderboard_monthly AS
SELECT m.user_id, p.display_name, p.username, COUNT(*) AS meal_count
FROM meals m JOIN profiles p ON p.id = m.user_id
WHERE m.status = 'approved' AND m.created_at >= now() - interval '30 days'
GROUP BY m.user_id, p.display_name, p.username ORDER BY meal_count DESC;

CREATE VIEW leaderboard_semester AS
SELECT m.user_id, p.display_name, p.username, COUNT(*) AS meal_count
FROM meals m JOIN profiles p ON p.id = m.user_id
JOIN semesters s ON s.id = m.semester_id
WHERE m.status = 'approved' AND CURRENT_DATE BETWEEN s.start_date AND s.end_date
GROUP BY m.user_id, p.display_name, p.username ORDER BY meal_count DESC;

-- Seed semester
INSERT INTO semesters (name, start_date, end_date)
VALUES ('Summer 2026', '2026-06-01', '2026-08-15');
```

### 6. Registration Bug Fix

**Problem:** Signing up threw "new row violates row-level security policy for table profiles."

**Root cause:** Supabase had email confirmation enabled by default. After `signUp`, the user has no active session yet, so `auth.uid()` is null and the profile INSERT fails the RLS check.

**Secondary issue discovered:** Even with email confirmation disabled, the DB trigger creates an empty profile row first. `auth.js` then tried to INSERT again (conflict code 23505), which was silently caught — meaning `display_name` and `username` were never actually saved.

**Fixes applied:**
1. Disabled email confirmation in Supabase → Authentication → Providers → Email → "Confirm email" OFF
2. Changed `auth.js` profile INSERT to UPDATE (the trigger handles the INSERT, auth.js then fills in the name/username):

```js
// Before
const { error: profileError } = await supabase
  .from('profiles')
  .insert({ id: data.user.id, display_name: displayName, username })
if (profileError && profileError.code !== '23505') throw profileError

// After
const { error: profileError } = await supabase
  .from('profiles')
  .update({ display_name: displayName, username })
  .eq('id', data.user.id)
if (profileError) throw profileError
```

**Additional note:** First signup attempt had already created a ghost user in Supabase auth. Had to delete it manually via Authentication → Users before the fixed signup would work.

### 9. Moderation Page 400 Error

**Problem:** Loading `moderation.html` threw a 400 error — "Failed to load resource."

**Root cause:** The query uses `profiles:user_id(...)` to join the `profiles` table, but `meals.user_id` only had a FK to `auth.users(id)`, not to `profiles(id)`. Supabase/PostgREST couldn't resolve the join and rejected the request. Same issue affects the dashboard carousel and profile page queries.

**Fix — run in Supabase SQL Editor:**
```sql
ALTER TABLE meals ADD FOREIGN KEY (user_id) REFERENCES profiles(id) ON DELETE CASCADE;
```

### 11. Sign In Button Refreshing Index Page

**Problem:** Clicking "Sign In" on `index.html` appeared to just refresh the page.

**Root cause:** The user was already logged in. `auth.js` had a session check at the bottom that redirected authenticated users away from `login.html` — but it was redirecting to `index.html`, making it look like a refresh.

**Secondary issue:** Even when not logged in, the login page would flash briefly before auth check completed, because the page rendered before the async `getSession()` resolved.

**Fixes in `js/auth.js` and `login.html`:**

1. Changed redirect destination from `index.html` to `profile.html`:
```js
// Before
if (session) window.location.href = 'index.html'

// After — redirect to profile if already logged in
if (session) {
  window.location.href = 'profile.html'
} else {
  document.body.style.visibility = 'visible'
}
```

2. Added `body { visibility: hidden; }` to `login.html` so the page stays invisible until the session check resolves — eliminates the flash.
